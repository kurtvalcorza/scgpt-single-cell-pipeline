## Two things this tutorial does that the fleet's others do not

**It carries the model architecture itself.** The Hub repository ships no model code, so `build_model()` in the carried `pipeline.py` rebuilds the scGPT encoder on plain torch modules and the weights load with `strict=True`. Nothing from the Hub, Dataverse or PyPI beyond torch is executed to build the model, and `transformers` is not installed at all.

**One manifest entry comes from a second source.** The gene vocabulary is not in the Hub repository; the inline `MANIFEST` lists it with its Harvard Dataverse file id as `source`, `stage_missing_files` fetches it from there, and `verify_snapshot` checks its digest with the rest. The generator's Section 3 prose describes Hub staging; the vocabulary entry's `source` and `note` fields in the inline manifest literal, and the intro, say where that one file comes from.

## Conformance notes

- **Standalone carrier (ST1–ST8):** the primary path performs no clone, repository install, or repository import. Section 2 embeds the repository's 3 modules (`pipeline.py`, `samples.py`, `metrics.py`) verbatim in topological dependency order (each tagged `metadata.dimer.embedded_module`; the only rewrites make `DEFAULT_WEIGHTS_DIR` working-directory-relative and remove internal relative package imports), Section 3 carries the 4-file snapshot manifest inline and asserts it against the module's own identity constants before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision, the module SHA-256 digests, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried modules, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD9):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent — Hub files from the Hugging Face Hub at the immutable revision (never `main`), the vocabulary from its persistent Dataverse file id; `verify_snapshot` re-hashes every entry; `ScGPTPipeline.from_pretrained(weights_dir=...)` then asserts the pinned config against the package constants, validates the vocabulary, builds the encoder and loads the safetensors with `strict=True`. The `scgpt_gh_repo_original_model.bin` pickle is not in the manifest and is never loaded (MOD9); no remote code is executed. The notebook never imports `huggingface_hub`, `safetensors` or `urllib` for model work outside the carried module cells.
- **Stages (§4.1):** `generate_sample_dataset` / `load_byod_dataset` (sample acquisition) → `validate_dataset` with the vocabulary (validation, with encodability, the ceilings and a dataset digest) → `split_dataset` (stratified train/validation/test) → `bin_expression` + `validate_inputs` with rejection and truncation probes → `pipe.embed` (representations, with same-batch identity and gene-order-invariance assertions) → `pipe.predict_masked` + `pipe.predict_masked_genes` (the pretraining objective, reported as it comes) → `pipe.nearest_centroid_evaluate` + `majority_baseline` + `library_size_baseline` (fitted on the training split only) → `pipe.adapt` (bounded gradient fine-tuning, real on the default path, RUN7/FT2) → `pipe.evaluate` (held-out metrics, deltas against the centroid rule and majority) → `pipe.classify` (new-data inference) → `pipe.save_artifact` (export + provenance) → `ScGPTPipeline.from_artifact` (fresh-boundary reload and parity assertion).
- **Score semantics (UNC1–UNC4):** the per-class scores are softmax outputs of a head trained on 36 synthetic cells, **not calibrated probabilities**; the only decision rule is argmax, and deployment thresholding is the caller's. Embeddings are labelled as representations with no intrinsic metric (EVAL9). The masked-expression numbers are labelled as a probe of the shipped decoder and read as a negative result where they are one.
- **Baselines and evidence (EVAL6/EVAL10/EVAL11):** the zero-training nearest-centroid rule, the majority rule and the library-size threshold are computed on the same test split as the adapted model, and every metric is labelled as tutorial sample-sanity evidence from one seeded holdout with no dispersion estimate. The sample equalises library size and detected genes by construction, which is what makes the library-size baseline informative, and builds its classes from real marker programmes, which is what makes the frozen-embedding baseline informative.
- **Split integrity (SPL1–SPL8):** the split is explicit, stratified and seeded; validation metrics are used for per-epoch monitoring only and the final epoch's weights are kept, so the test split is never used for selection. The notebook states that random splitting assumes independent cells and that cells from one donor, plate or batch leak — split by that grouping on real data.
- **Ceilings (VAL6):** `MAX_GENES_PER_CELL = 1535` (truncation to the most expressed, reported), `MAX_CELLS_PER_CALL = 32`, `MIN_DETECTED_GENES = 10`, the vocabulary size and special ids, and the record and class minimums and maximums are printed from the schema and the dataset manifest before the model runs; four rejections and one truncation are demonstrated, and scale invariance of the binning is asserted.
- **BYOD (DAT10–DAT19):** `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog; when enabled, user data flows through the same validation, split, baselines, adaptation, evaluation, inference, export and reload cells. The expected schema, the gene-symbol convention (HGNC symbols, not Ensembl ids) and the privacy guidance — a patient-derived matrix is restricted data — are stated in the Prerequisites and in Section 4, and the sample dataset is written to `outputs/scgpt_single_cell_sample_dataset.csv` in the genes-as-columns shape as a template.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.
